# MC 26.1 Port — Implementation Plan

**Date:** 2026-05-01
**Branch:** `port/26.1` (off `feat/czechcraft-v1`)
**Goal:** Single-target retarget of CzechCraft v1.0.0 from MC 1.21.1 (Yarn / Loom 1.7 / Java 21) to **MC 26.1.x** (Mojang mappings / Loom 1.15 / Java 25 / Gradle 9.5).

Strategy: **Strategy 1 — single-target retarget** (per the May 2026 brainstorm — see git log for the discussion). One source tree, no preprocessor, no in-source version forks. 1.21.1 audience preserved via `snapshot/1.21.1-pre-port` git tag and the closed PR #1 — only revived (Strategy 2 frozen branch) if Modrinth issues request it.

**Reference mods used to verify named symbols:** [fabric-example-mod `26.1`](https://github.com/FabricMC/fabric-example-mod/tree/26.1), [DaRealTurtyWurty/26.1-TutorialMod](https://github.com/DaRealTurtyWurty/26.1-TutorialMod), [jimflood/kitty-cat-mod](https://github.com/jimflood/kitty-cat-mod). Keep these open during the port.

---

## Acceptance criteria (definition of done)

- `./gradlew build` succeeds clean on JDK 25 / Gradle 9.5 / Loom 1.15.5.
- `./gradlew :fabric:runDatagen` regenerates the same set of files (recipe, model, two lang files, item tag if any) under `fabric/src/main/generated/`.
- `./gradlew :fabric:runClient` launches MC 26.1.2, Rohlík renders in the creative tab with the correct illustration and Czech/English names, the 2-wheat shaped recipe works in both 3×3 and 2×2 grids, eating restores 2 hunger.
- `./gradlew :fabric:modrinth --dry-run` walks the task graph cleanly (no upload).
- `DatagenOutputTest` passes.
- New `common/test/` JUnit suite passes (resurrected unit tests for `FoodItems` and `ModItems` field values, gated on `fabric-loader-junit` bootstrap).
- CI green on the PR.
- `CLAUDE.md`, `README.md`, `gradle.properties` reflect the new toolchain. The "no JUnit in common/" gotcha is removed from `CLAUDE.md`.

### Step 6 — `Item.Properties.setId(ResourceKey)` refactor

**This is the only structural code change.** In 26.1, every `Item` must know its ID at construction time via `new Item.Properties().setId(ResourceKey<Item>)` *before* `new Item(props)`. Our current pattern constructs `FoodItems.ROHLIK` first, then registers via `add("rohlik", ROHLIK)` later — that no longer works.

**Refactor pattern (mirrors TutorialMod `ModItems.EXAMPLE_FOOD`):**

1. In `FoodItems` (and any future content class): change static fields from `public static final Item ROHLIK = new Item(...)` to a factory style that takes a path:
   ```java
   public static Item createRohlik() {
       ResourceKey<Item> key = ResourceKey.create(Registries.ITEM, Identifier.fromNamespaceAndPath(CzechCraft.MOD_ID, ROHLIK_PATH));
       return new Item(new Item.Properties().setId(key).food(rohlikFood(), rohlikConsumable()));
   }
   ```
2. In `ModItems`: invoke factories in the static init and store the result:
   ```java
   public static final Item ROHLIK = add(FoodItems.ROHLIK_PATH, FoodItems.createRohlik());
   ```
3. Keep the `add(path, item)` API on `ModItems` — it still serves as the "central registry of CzechCraft items", just with a different argument flow.

**For `.snack()` replacement:** the simplest port is to drop it (default eat speed). If we want fast-eat behaviour explicitly, attach a `Consumable` via `.food(props, consumable)`:
```java
import net.minecraft.world.item.consume_effects.Consumables;   // verify exact package at compile time
private static Consumable rohlikConsumable() {
    return Consumables.defaultFood();   // or .builder().consumeSeconds(0.8f).build() for snack speed
}
```

**Acceptance:** `FoodItems` and `ModItems` compile. `ROHLIK` is still accessible as a `static final Item` for `ModItemGroups.mainGroupIcon()` and creative-tab population.

### Step 7 — `CzechCraftItemGroupFabric` rewrite

Apply renames from Step 5 + the structural shift documented above. Reference: TutorialMod's `FabricRegistryHelper.java`. Skeleton:

```java
public final class CzechCraftItemGroupFabric {
    public static void register() {
        CreativeModeTab tab = FabricCreativeModeTab.builder()
            .icon(ModItemGroups::mainGroupIcon)             // returns ItemStack
            .title(Component.translatable(ModItemGroups.MAIN_GROUP_TRANSLATION_KEY))
            .displayItems((displayContext, entries) -> ModItems.getAll().forEach(entries::accept))
            .build();
        Registry.register(BuiltInRegistries.CREATIVE_MODE_TAB, ModItemGroups.MAIN_GROUP_ID, tab);
    }
}
```

`ModItemGroups.MAIN_GROUP_ID` must now be a `ResourceKey<CreativeModeTab>` (not `Identifier`) — adjust the constant.

**`ItemStackTemplate` consideration:** `ModItemGroups.mainGroupIcon()` constructs `new ItemStack(item)`. Because the icon supplier is *called by the creative tab at open-time* (post-world-load), this is safe. **No change needed.** If a compile error or runtime warning surfaces, switch to `ItemStackTemplate`.

**Acceptance:** Fabric module compiles.

### Step 8 — Datagen providers

Apply renames first:
- `FabricDataOutput` → `FabricPackOutput`
- `RegistryWrapper.WrapperLookup` → `HolderLookup.Provider` (`net.minecraft.core.HolderLookup`)
- `RecipeExporter` → `RecipeOutput`
- `ShapedRecipeJsonBuilder.create(...)` → `shaped(...)` (static helper on `RecipeProvider`)
- `conditionsFromItem(item)` → `has(item)` + `unlockedBy(getHasName(item), has(item))`

Then handle the structural change in `ModRecipeProvider`:
- The override pattern shifted. Instead of overriding `generate(RecipeExporter)`, override `protected RecipeProvider createRecipeProvider(HolderLookup.Provider, RecipeOutput)` and return a `RecipeProvider` whose `buildRecipes()` produces our shaped recipe. Verify against fabric-api testmod sources after Step 2's dependency refresh — `./gradlew :fabric:dependencies` will reveal the source jar.

For `ModModelProvider`: the `register(item, Models.GENERATED)` pattern moved to `itemModelOutput.accept(item, plainModel(item, Models.GENERATED))` or similar in 1.21.4+. Resolve via compile errors with TutorialMod's NeoForge-side `ModItemModelProvider` open as reference.

For `BaseLangProvider` and subclasses: only signature changes — `FabricPackOutput`, `HolderLookup.Provider`. `TranslationBuilder.add(...)` API is unchanged.

`CzechCraftDataGenerator`: only the `Pack.addProvider` lambda may need adjustment depending on constructor sig of providers above.

**Acceptance:** `./gradlew :fabric:runDatagen` succeeds. Generated files in `fabric/src/main/generated/` have content equivalent to today's output (paths/IDs unchanged; JSON shape may differ slightly per Mojang's data format evolution — eyeball-diff and accept differences that are not regressions).

3. Add `@BeforeAll` bootstrap:

   ```java
       Bootstrap.bootStrap();
   }
   ```

## Risk register

| Risk | Likelihood | Mitigation |
|---|---|---|
| `FabricRecipeProvider` API has different override pattern than expected | Medium | Compile error reveals exact signature; refer to fabric-api testmod source via `./gradlew :fabric:dependencies --configuration testCompileClasspath` |
| `Consumable` API for `.snack()` replacement has different namespace | Medium | TutorialMod `ModFoods.java` uses `Consumables.defaultFood()` — open as reference at Step 6. Worst case: drop `.snack()` and accept default eat speed (cosmetic only) |
| Spotless 7 formatter rules differ from 6 | Low | Run `spotlessApply` once to normalize; commit the diff separately |
| Loom 1.15 + minotaur classloader collision returns | Low | Already mitigated by root-level `apply false` pattern. Verified safe by issue #80 / #75 closure. Detected by `:fabric:modrinth --dry-run` |
| `ItemStack` pre-world-load construction in `mainGroupIcon` | Low | Lazy supplier; called post-world-load. If runtime warns, swap to `ItemStackTemplate` |
| Datagen output JSON shape changed enough that `DatagenOutputTest` needs rewrite | Low | Test asserts file presence + key fields; update only if a meaningful semantic changed |
| Hidden API rename in our datagen providers we missed | Medium | Compile-driven discovery — bounded to ~5 datagen classes |
